# Mobile app

The decisions of epic #264, taken before any of the app existed. The investigation behind them
(options compared, with sources) is on the epic itself; this page keeps what was decided, why, and
what was turned down.


## Expo, rather than native apps or a WebView

*Accepted · 2026-10-10 · #269*

**Decision.** The app is written with **Expo**, the framework on top of React Native, in
TypeScript: one code base, rendered as the platform's own widgets on iOS and Android.

**Why.** Of the options compared, it reuses the most of what exists without inheriting the
website's UI: the generated wire types, the ahead-of-time validators, the de/en texts and the
date and importance rules, shared between `frontend/` and the app. React stays the
idiom, so the same knowledge applies on both sides. And Gunnar is using Expo in another project,
so what is learnt here carries over.

**Rejected.**

- **Native apps, Swift and Kotlin.** The reference for each platform, but every feature twice and
  nothing shared, not even the validation. For a demo whose website already does everything, that
  is twice the work for a UI that is not much better.
- **Kotlin Multiplatform with Compose Multiplatform.** The strongest alternative, and the nearest
  thing to the backend's Java. It reuses nothing from the frontend, and its shared UI does not
  look like an iOS app.
- **Flutter.** Mature, but a third language and its own renderer, offering nothing here that
  Expo or Kotlin Multiplatform does not offer better.
- **Capacitor**, the website in a WebView. The fastest path to parity, but the UI stays the
  website's, and every request and the sign-in have to change anyway.
- **A PWA.** The website, installable. It is not the app that was asked for, and on iOS push
  reaches it only after the user adds it to the home screen.

**Cost.** The screens are new: `<div>` and CSS become `<View>` and `StyleSheet`. Only the logic
underneath is shared.


## Native projects are generated, and builds run on GitHub Actions

*Accepted · 2026-10-10 · #269*

**Decision.** `ios/` and `android/` are generated by `expo prebuild` from the app's configuration
and are never committed. Builds run on GitHub Actions, iOS on macOS runners and Android on Linux.
Expo's build service, EAS, is not used.

**Why.** Generated Xcode and Gradle projects in the repository would be reviewed and could drift
from the configuration. Running the builds in our own CI keeps everything that can be enforced
in CI, as for the backend and the website. It costs nothing, since GitHub's hosted runners are
free for a public repository, macOS included.

**Rejected: over-the-air updates (EAS Update), for now.** They would let JavaScript changes reach
installed apps without a store build. That is attractive, but it makes "which version is
installed" fuzzy just as apps start to have a minimum version. They can be added later without
changing anything else.


## The app imports the website's code; a `shared/` package can wait

*Accepted · 2026-10-10 · #286*

**Decision.** The app takes the website's generated wire types and validators, its de/en texts
and its date and importance rules straight from `frontend/src`, through the one module
`mobile/src/web.ts` (`doc/mobile/development.md`). There is no `shared/` package yet, though #267
first asked for one.

**Why.** The direct import already gives what the package was for: one copy, used by both, and
drift caught by the website's own tests and generators. A package would move those files out of
`frontend/src`, which changes the imports of existing frontend tests, and it adds an npm workspace
to the build, CI caches and Renovate for no gain today. `web.ts` keeps the door open: everything
the app borrows goes through it, so a later move changes that one file on the app's side.

**Revisit when** a third consumer appears, the website needs something only the app has, or the
app's bundler or test runner stops resolving `frontend/src` cleanly. Gunnar decided this on #267,
on 10 October 2026, and asked for it to be reviewed later.

## The app sends Google's ID token as a bearer token

*Accepted · 2026-10-10 · #269*

**Decision (S1 on #264).** The app signs in with the platform's Google SDK (Credential Manager on
Android, the Google Sign-In SDK on iOS) and sends the ID token as `Authorization: Bearer`. The
backend accepts that beside its session cookie. The app signs itself out after **30 days without
use**. The **website's session stays as it is**: eight hours without a request.

**Why client-side at all.** The website's backend-for-frontend does not carry over to an app.
Google refuses sign-in inside an embedded WebView, and a cookie set in the system browser is not
visible to the app. RFC 8252 (OAuth for native apps) says what to do instead: the system browser
or the platform's own sign-in, PKCE, and the tokens on the device. Google narrows that further for
mobile clients, with no custom URI schemes on Android, no loopback redirects and no client
secret, and recommends its native SDKs.

**Why S1.** It is the smallest backend change and the closest to the standard: the backend
validates a token from an issuer it already trusts, and nothing else changes.

**Rejected.**

- **S2:** the backend exchanges a one-time code and gives the app a session of its own. That
  keeps Google's tokens server-side, as on the web, but it needs a session store or a second
  encrypted token format.
- **S3:** a broker such as Cognito in front of Google. It is provider-neutral, but it is a new
  component, and the website's sign-in would either move to it or differ from the app's.

**Why the month belongs to the app.** In S1 the backend only ever sees short-lived ID tokens,
which the SDK renews silently. There is nothing on the server to expire, so the rule lives where
the session does.

**Cost.** The qa test accounts (Cognito) have to accept bearer tokens too, or there is no
automated sign-in for the app's tests. The app signs them in with code + PKCE through the system
browser.

**The library: react-native-nitro-google-signin (#280).** It wraps Credential Manager and the
Google Sign-In SDK, as decided, under the MIT licence, and comes with an Expo config plugin. The
widely used `@react-native-google-signin/google-signin` was the obvious alternative, but its free
version still uses Google's deprecated Android sign-in SDK; Credential Manager is in its paid
edition. A module of our own over the two SDKs stays the fallback if the library falls behind.

**Google's button is the website's image, not the library's native one (#325).** The library
offers Google's native button (`GIDSignInButton` on iOS, Play services' assets on Android), but it
is a native view the Jest tests cannot render, and its words follow the phone's language where the
website's are always Google's English. The website's PNGs are Google's official button too,
already in use, the same on both platforms, and testable like any other image. A button of our
own would have been allowed as well: Google's
[branding guidelines](https://developers.google.com/identity/branding-guidelines) ask only that
its "G" keep its size and colours, and permit the words in the app's language. Using the image is
our choice, for one look on every platform, not Google's requirement.

**Attaching files: Expo's own modules (#274).** expo-image-picker for the camera and the photo
library, expo-document-picker for any file — not expo-file-system's own `File.pickFileAsync`,
whose file Android names after its content URI (`image:1000000018`, as the Maestro flow showed)
rather than the name the user sees — expo-file-system's `File.upload` for the PUT to storage, with
progress, expo-image-manipulator for thumbnails and HEIC, and expo-intent-launcher to
hand a PDF to Android's viewer. All are Expo SDK modules, versioned with the SDK, so an SDK update
moves them together; none needs a native module of our own.

**One web client for qa and prod** (Gunnar, #280). Both apps ask for ID tokens for the web client
the website uses, so a qa token would be accepted by prod as well. That gives no one more than a
sign-in to prod gives them already, and separate clients would only pay off with separate users or
consent screens.


## Sign in with Apple comes later; a hidden address is a separate account

*Accepted · 2026-10-10 · #286*

**Decision.** Sign in with Apple is planned: Apple and Google together cover nearly every phone.
It is not part of the first stories.

**Hidden addresses.** The email is the identity
([The email stays the identity](authentication.md#the-email-stays-the-identity-and-every-provider-must-verify-it)).
Apple's *Hide My Email* gives each app a relay address, so the same person signing in with Google
and with a hidden Apple address has two accounts, two boards. That is accepted, and the sign-in
page says so (Gunnar, #264, 10 October 2026).

**Rejected: the identity as issuer and subject.** It would join the two, but it reopens D1 of #141
and changes the domain for a case one sentence on the sign-in page covers.


## Push goes through Amazon SNS; reminders are local

*Accepted · 2026-10-10 · #269*

**Decision.**

- **Changes push to the user's other devices.** A task created, changed or deleted, on the
  website or on another phone, becomes a visible notification on the user's devices, except the
  one that made the change. It is sent through **Amazon SNS** mobile push, to APNs and FCM.
- **Due-date reminders are local notifications**, scheduled by the app itself: one summary at
  **08:00 local time on the due day** ("3 tasks due today"). Push keeps them current when a task
  changes elsewhere.

**Why SNS.** It fits the AWS and OpenTofu setup that is already there, with IAM rather than one
more credential in the backend. At this volume it costs nothing: the first million notifications
a month are free. The backend's tasks already have public IPs, so no VPC endpoint is needed.
Choosing it is easy to undo; sending straight to APNs and FCM would be the alternative.

**Why reminders are not pushed.** A local notification works offline and needs no scheduler on
the server, no device tokens and nothing new in the privacy policy. The due date is a day without
a time, so "08:00 on the day" is a choice rather than a fact, and making it per user is a later
setting.

**Cost.** Push needs a new domain concept, the **device**: an app installation that belongs to a
user and is deleted with the account. It also needs an APNs key from Apple and a Firebase project
for FCM, which FCM requires even through SNS.

**A notification carries the task's description**, not only "a task was added" (Gunnar, #264,
10 October 2026). It is what makes the notification worth having. The text passes through Apple's
and Google's push services, so the privacy policy names both.


## Readable offline, not editable offline

*Accepted · 2026-10-10 · #269*

Revised in part: a file's transfer is bounded by its size rather than ten seconds (below, #432).

**Decision.** The app keeps the last board it loaded and shows it without a connection. Changes
need a connection.

**How (#272).** One JSON file in the app's cache directory, written after every load: the board is
a copy of the backend's, small, and only ever read whole, so a database or a persisted query cache
would add a dependency for nothing. It names its account, is removed on sign-out, and while it is
shown — before the load, or after one failed — every change is refused rather than sent.

**A connection that hangs counts as none (#311).** Every request the app makes over the network
fails after 10 seconds, its answer read in full, and is aborted (`withinLimit` and `REQUEST_MS` in
`mobile/src/timeLimit.ts`): the backend's, and the identity provider's -- its discovery document,
the code exchange after signing in, and renewing the tokens. Without that, a connection that hangs
rather than drops was waited on without end: the board said it was loading instead of showing the
kept one with "No connection", and a change neither went through nor failed. Ten seconds is long
for an answer the backend gives in well under one, and short enough that nobody gives up on the app
first. Two exceptions: the sign-in in the browser takes as long as its user does, and the version
check at start gives up after three seconds (`VERSION_CHECK_MS`), since the start waits for it.

A file's transfer to or from storage is held to the same rule, by its size rather than ten seconds
(#432): ten seconds, and the file's bytes at 64 KiB/s, a poor mobile connection (`transferMs`), and
the native transfer is aborted when the time is up. That is the upload's PUT, by the file's own
size, and the downloads of a preview and of a document Android opens, by the largest file the
backend takes (10 MB, 170 s), since their size is not known before they arrive. Without it, a
transfer that hung left the upload shown, or a file being opened, for the rest of the run, and the
app never started over in the foreground. Watching for a transfer that stops making progress would
end a hung one sooner; a bound by size is the smaller change, and one rule for all three.

A change that got no answer in time may have reached the backend all the same, its answer only slow.
So it is reported as failed, as before, and the board is loaded again at once: it shows whether the
change arrived, and until a load works the board counts as possibly out of date and refuses changes
(see above), so a second try is never sent blind and cannot add a task twice. That holds for an undo
too, whose restore is two requests and may have done only the first.

**Why not more.** Editing offline means queueing changes. Because an update sends the whole task,
a queued change would silently overwrite a newer one. That needs a version per task, optimistic
locking, before it can be built, and it is worth its own story, which would help the website too.


## Releases follow semantic versioning, measured by the API

*Accepted · 2026-10-10 · #269*

**Decision.**

- **The version number says what changed in the API.** Major is a change an installed app cannot
  handle, minor a compatible addition, patch neither.
- **A gate enforces it.** CI compares the published API with the oldest supported release and
  fails on a breaking change.
- **Too-old apps are told to update.** The backend announces a minimum app version.
- **Breaking changes get a new path.** `/api/v2/...` would be served beside today's paths for as
  long as supported apps need them.
- **The first release apps are built against is 1.0.0** (11 October 2026). The app builds
  themselves follow during the 1.x cycle, with distribution (#276).

**Why.** Until now the website was the only client and always deployed with its backend, so the
API could change in one step. An installed app is weeks old and must keep working. Under 0.x,
semantic versioning promises nothing, so the promise starts with the release the first apps are
built against, before any is out: an app shipped later in 1.x can rely on it from the start.


## Testers only, one app per environment

*Accepted · 2026-10-10 · #269*

**Decision.** The app reaches phones through TestFlight and Google Play internal testing, not
the public stores. There are three variants, installable side by side:
- **`de.hilling.taskfest`**, against prod;
- `de.hilling.taskfest.qa`, against qa;
- `de.hilling.taskfest.dev`, against the local stack.

**Why.** The aim is the experience of building and shipping an app, not public distribution. The
build that goes to testers is the same signed release build a store takes, so a public release
would be a decision, not a project.

**Developer accounts: organization, for both.** Apple and Google accounts are opened for
**Hilling IT GmbH**, which has a D-U-N-S number, so the stores name the company as the seller
(Gunnar, #264, 10 October 2026). An organization account on Google Play is also exempt from the
closed test of 12 testers for 14 days that a personal one needs before a public release.


## Uploads with the plain tools: cloud signing on iOS, no stored Google key

*Accepted · 2026-10-17 · #276, #318*

Revised in part: a store release also waits for Gunnar's approval
([Store releases wait for Gunnar's approval](#store-releases-wait-for-gunnars-approval), #363).

**Decision.** The release workflow uploads with the platforms' own tools, not fastlane:
`xcodebuild` signs and uploads to TestFlight, Gradle signs the bundle and a small script calls
Google Play's publishing API. iOS signs with Apple's **cloud-managed distribution certificate**,
through an App Store Connect API key with the Admin role (Gunnar, #276, 16 October 2026). Google
is reached through **Workload Identity Federation**, with no service-account key. The store
credentials are secrets of an environment that admits release tags only.

**Why.** fastlane would bring Ruby and a Gemfile for two steps that the platforms' tools do in one
call each, and its own layer to debug when they fail. Cloud signing leaves nothing to renew: no
certificate or provisioning profile to export, store and replace every year. The price is a key
with the Admin role, which could do far more in App Store Connect than upload; keeping it in a
tag-only environment is what makes that acceptable. Workload Identity Federation is the same idea
as the AWS deploy roles: GitHub's OIDC token buys a short-lived one, so there is no key to leak,
and new Google Cloud organizations refuse service-account keys by default anyway.

**Rejected: a certificate and profiles as secrets.** It would need only an App Manager key, but
a certificate made on a Mac, two profiles, and their renewal every year.

**Decision.** No Sentry, Crashlytics or similar.

**Why.** Each one is a further processor for the privacy policy. It can be added later.

## Sharing into the app with expo-sharing, reading only the raw share

*Accepted · 2026-10-20 · #355, #357*

**Decision.** Sharing into TaskFest (#279, #355) uses Expo's own **expo-sharing**: its config
plugin declares Android's intent filters and generates iOS's share extension (#356), and the
release signs that with its App Group ([distribution.md](../mobile/distribution.md)). The app reads
only the raw share and copies a shared file itself; it never asks the library to "resolve" one.
On iOS, the extension opens the app with the trick every such library uses; Gunnar accepted
App Review's risk (20 October 2026).

**Why.** It is versioned with the SDK and updated with it, where `expo-share-intent` does the same
with one maintainer and a release cycle of its own. Resolving would request a shared link to learn
its type, which nobody sharing a link expects of a task list. On Android it would also copy a file
to the top of the app's cache under whatever name the sending app gives: the kept board's
`board.json` is there, and a name with "../" goes further.

**What it costs.** A file's name is the end of its link, so one shared from Android's Files app,
whose links end in a document's number, is named by its type — `shared.png`. Apps that share
through their own file links keep their names.

**Rejected: a form of its own in the share sheet**, as Todoist's is. It would be a second task
form, in Swift, kept in step by hand, and a task is finished in the app anyway: its due date at
least.

**If App Review rejects the trick**, the extension saves the share and says *"Saved. Open TaskFest
to finish it."*; the app's side stays as it is, since it looks for a share whenever it becomes
active. That needs a small extension of the project's own, a few lines of Swift, as the plan on
#279 describes.

## expo-sharing is patched for a shared page's title

*Accepted · 2026-10-30 · #414*

**Decision.** A link shared from a browser becomes a link titled by its page (#414), and the
title comes from what the browser already sends beside the link, through two patches to
expo-sharing: on iOS, `withPageTitle` rewrites its extension template during prebuild, as
`withFolderPerFile` does; on Android, `patch-package` applies `mobile/patches/` to its Kotlin parser
on every `npm ci`, and `package.json` has autolinking build expo-sharing from that source
(`expo.autolinking.android.buildFromSource`) -- Expo ships its modules for Android precompiled, and
the first APK with the patch never saw it. Both fail loudly when an update moves the code they change: the first throws
during prebuild, the second fails the install, and `src/patches.test.ts` fails when the patch did
not run.

**Why patches.** expo-sharing's JavaScript side passes on only the share's text and files: Safari's
title (the item's attributed content text) and Chrome's (the intent's subject) never reach it. The
patches add the title as one more text item, so the JavaScript side and "reading only the raw
share" stay as they are. Gunnar chose to patch Android too rather than leave its description empty.

**Rejected: fetching the page for its title**, which would request the shared link -- the very
thing the app does not do. **Rejected for Android: a module of the app's own** reading the launch
intent beside expo-sharing, which would mean a second reader of the same intent for one field.

## Store releases wait for Gunnar's approval

*Accepted · 2026-10-31 · #363*

**Decision.** The `app-stores` environment has Gunnar as its required reviewer, as `prod` has. A
release's two store jobs reach it together, and one approval in the run lets both through. `qa`
and `qa-live-test` admit `main` and `v*` tags only, as `prod` does, without a reviewer.

**Why.** The review apps, CodeRabbit and Greptile, may write the repository's contents and
workflows, so a breach of either could push a `v*` tag that points at a workflow of its own. The
tag-only rule admits it, and the store credentials, the Admin key among them, would be in its
hands. A reviewer is the one thing such a tag cannot get past. The apps are trusted; this is the
fallback for their breach. qa is open to testers only, so a forged tag deploying there is the
risk accepted; the branch policy keeps a workflow on any other branch from deploying there at all,
since the deploy and live-test roles trust a job by its environment's name.

**Cost.** One click per release before it reaches TestFlight and Play. A release nobody approves
uploads nothing, and GitHub fails the waiting jobs after 30 days.

**Rejected: a tag ruleset that lets only Gunnar create `v*` tags.** `cut-release.yml` (#297)
creates the tag with the workflow's own token, so GitHub Actions would have to bypass the ruleset,
and then any workflow pushed on a branch could create the tag in its place. Tagging through a token
of Gunnar's, kept in an environment only `main` reaches, would hold, at the price of a token to
create and renew; tagging by hand would retire `cut-release.yml`. Neither is worth it for a fallback.
