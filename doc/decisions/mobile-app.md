# Mobile app

The decisions of epic #264, taken before any of the app existed. The investigation behind them
(options compared, with sources) is on the epic itself; this page keeps what was decided, why, and
what was turned down.


## Expo, rather than native apps or a WebView

**Decision.** The app is written with **Expo**, the framework on top of React Native, in
TypeScript: one code base, rendered as the platform's own widgets on iOS and Android.

**Why.** Of the options compared, it reuses the most of what exists without inheriting the
website's UI: the generated wire types, the ahead-of-time validators, the de/en texts and the
date and importance rules, shared as a package between `frontend/` and the app. React stays the
idiom, so the same knowledge applies on both sides. And Gunnar is using Expo in another project,
so what is learnt here carries over.

**Rejected.**

- **Native apps, Swift and Kotlin.** The reference for each platform, but every feature twice and
  nothing shared, not even the validation. For a demo whose website already does everything, that
  is twice the work for a UI that is not much better.
- **Kotlin Multiplatform with Compose Multiplatform.** The strongest alternative, and the nearest
  thing to the backend's Java. It reuses nothing from the frontend, and its shared UI does not
  look like an iOS app.
- **Flutter.** Mature, but a third language and its own renderer, offering nothing here that
  Expo or Kotlin Multiplatform does not offer better.
- **Capacitor**, the website in a WebView. The fastest path to parity, but the UI stays the
  website's, and every request and the sign-in have to change anyway.
- **A PWA.** The website, installable. It is not the app that was asked for, and on iOS push
  reaches it only after the user adds it to the home screen.

**Cost.** The screens are new: `<div>` and CSS become `<View>` and `StyleSheet`. Only the logic
underneath is shared.


## Native projects are generated, and builds run on GitHub Actions

**Decision.** `ios/` and `android/` are generated by `expo prebuild` from the app's configuration
and are never committed. Builds run on GitHub Actions, iOS on macOS runners and Android on Linux.
Expo's build service, EAS, is not used.

**Why.** Generated Xcode and Gradle projects in the repository would be reviewed and could drift
from the configuration. Running the builds in our own CI keeps everything that can be enforced
in CI, as for the backend and the website. It costs nothing, since GitHub's hosted runners are
free for a public repository, macOS included.

**Rejected: over-the-air updates (EAS Update), for now.** They would let JavaScript changes reach
installed apps without a store build. That is attractive, but it makes "which version is
installed" fuzzy just as apps start to have a minimum version. They can be added later without
changing anything else.


## The app sends Google's ID token as a bearer token

**Decision (S1 on #264).** The app signs in with the platform's Google SDK (Credential Manager on
Android, the Google Sign-In SDK on iOS) and sends the ID token as `Authorization: Bearer`. The
backend accepts that beside its session cookie. The app signs itself out after **30 days without
use**. The **website's session stays as it is**: eight hours without a request.

**Why client-side at all.** The website's backend-for-frontend does not carry over to an app.
Google refuses sign-in inside an embedded WebView, and a cookie set in the system browser is not
visible to the app. RFC 8252 (OAuth for native apps) says what to do instead: the system browser
or the platform's own sign-in, PKCE, and the tokens on the device. Google narrows that further for
mobile clients, with no custom URI schemes on Android, no loopback redirects and no client
secret, and recommends its native SDKs.

**Why S1.** It is the smallest backend change and the closest to the standard: the backend
validates a token from an issuer it already trusts, and nothing else changes.

**Rejected.**

- **S2:** the backend exchanges a one-time code and gives the app a session of its own. That
  keeps Google's tokens server-side, as on the web, but it needs a session store or a second
  encrypted token format.
- **S3:** a broker such as Cognito in front of Google. It is provider-neutral, but it is a new
  component, and the website's sign-in would either move to it or differ from the app's.

**Why the month belongs to the app.** In S1 the backend only ever sees short-lived ID tokens,
which the SDK renews silently. There is nothing on the server to expire, so the rule lives where
the session does.

**Cost.** The qa test accounts (Cognito) have to accept bearer tokens too, or there is no
automated sign-in for the app's tests. The app signs them in with code + PKCE through the system
browser.


## Sign in with Apple comes later, and its hidden addresses are still open

**Decision.** Sign in with Apple is planned: Apple and Google together cover nearly every phone.
It is not part of the first stories.

**Open question.** The email is the identity
([The email stays the identity](authentication.md#the-email-stays-the-identity-and-every-provider-must-verify-it)).
Apple's *Hide My Email* gives each app a relay address, so the same person signing in with Google
and with a hidden Apple address would have two accounts. There are two ways out:
- accept that, and say so on the sign-in page;
- move the identity to issuer and subject, which reopens D1 of #141.

That is decided before Apple is added.


## Push goes through Amazon SNS; reminders are local

**Decision.**

- **Changes push to the user's other devices.** A task created, changed or deleted, on the
  website or on another phone, becomes a visible notification on the user's devices, except the
  one that made the change. It is sent through **Amazon SNS** mobile push, to APNs and FCM.
- **Due-date reminders are local notifications**, scheduled by the app itself: one summary at
  **08:00 local time on the due day** ("3 tasks due today"). Push keeps them current when a task
  changes elsewhere.

**Why SNS.** It fits the AWS and OpenTofu setup that is already there, with IAM rather than one
more credential in the backend. At this volume it costs nothing: the first million notifications
a month are free. The backend's tasks already have public IPs, so no VPC endpoint is needed.
Choosing it is easy to undo; sending straight to APNs and FCM would be the alternative.

**Why reminders are not pushed.** A local notification works offline and needs no scheduler on
the server, no device tokens and nothing new in the privacy policy. The due date is a day without
a time, so "08:00 on the day" is a choice rather than a fact, and making it per user is a later
setting.

**Cost.** Push needs a new domain concept, the **device**: an app installation that belongs to a
user and is deleted with the account. It also needs an APNs key from Apple and a Firebase project
for FCM, which FCM requires even through SNS. And Apple and Google see what is pushed, so the
privacy policy has to name them.


## Readable offline, not editable offline

**Decision.** The app keeps the last board it loaded and shows it without a connection. Changes
need a connection.

**Why not more.** Editing offline means queueing changes. Because an update sends the whole task,
a queued change would silently overwrite a newer one. That needs a version per task, optimistic
locking, before it can be built, and it is worth its own story, which would help the website too.


## Releases follow semantic versioning, measured by the API

**Decision.**

- **The version number says what changed in the API.** Major is a change an installed app cannot
  handle, minor a compatible addition, patch neither.
- **A gate enforces it.** CI compares the published API with the oldest supported release and
  fails on a breaking change.
- **Too-old apps are told to update.** The backend announces a minimum app version.
- **Breaking changes get a new path.** `/api/v2/...` would be served beside today's paths for as
  long as supported apps need them.
- **The first release with an app build is 1.0.0.**

**Why.** Until now the website was the only client and always deployed with its backend, so the
API could change in one step. An installed app is weeks old and must keep working. Under 0.x,
semantic versioning promises nothing, so the promise starts with the first app.


## Testers only, one app per environment

**Decision.** The app reaches phones through TestFlight and Google Play internal testing, not
the public stores. There are three variants, installable side by side:
- **`de.hilling.taskfest`**, against prod;
- `de.hilling.taskfest.qa`, against qa;
- `de.hilling.taskfest.dev`, against the local stack.

**Why.** The aim is the experience of building and shipping an app, not public distribution. The
build that goes to testers is the same signed release build a store takes, so a public release
would be a decision, not a project.

**Still open.** The Apple and Google developer accounts, individual or organization, and when
they are opened. Distribution and APNs wait for them.


## No crash reporting, for now

**Decision.** No Sentry, Crashlytics or similar.

**Why.** Each one is a further processor for the privacy policy. It can be added later.
